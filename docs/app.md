# digitus2 web app

The app in `apps/web` (`@digitus2/web`), built in milestone M4 from the plan `docs/superpowers/plans/2026-10-13-m4-app-mvp.md`. Product spec: `docs/superpowers/specs/2026-10-13-digitus2-design.md` (sections 4, 5 and 9). Verification spec: `docs/superpowers/specs/2026-10-13-verification-design.md` (goals "Be fast" and "Honor the design brief", checks 3.9 and 3.10). The technology choices and their measurements come from the rendering spike, `docs/research/rendering-spike.md`.

## What the app does

A beginner opens one of the 30 built-in pieces from a library grouped by level (or drops a MusicXML or MIDI file), and sees the score with a finger number on every note, chosen by the digitus2 engine for the selected hand size. Play sounds the piece on a sampled grand piano while a red cursor marks the notes being heard and an on-screen keyboard shows which finger plays which key; tempo, one hand or both, metronome, count-in and a bar loop help practice. Pieces with an editor's fingering can show it instead of the engine's. The fingered score can be exported as MusicXML or printed. An about page lists every licence and attribution. Everything runs in the browser: there is no server, and the only network traffic is the app's static files and the piano samples.

## Architecture

| ------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Shell               | `src/main.tsx`, `src/app/App.tsx`, `src/app/focus.ts`     | React 19 root; switches on the store's view: library, score or about. A view that replaces another moves the focus to its `h1` (`tabIndex={-1}`, no ring), so the next Tab starts inside the new view and a screen reader announces it; the view the page loads with leaves the focus alone.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Store               | `src/app/store.ts`                                        | One zustand store: the view, the open piece, a one-line notice, and the settings (hand size, tempo factor, hands, metronome, count-in, editor's fingering). Only the settings persist, in `localStorage` under `digitus2.settings.v1` (version 1); a stored object from an older or newer app is merged field by field with the defaults, unknown fields ignored.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Routes              | `src/app/routes.ts`                                       | The URL hash mirrors the view: `#/`, `#/about`, `#/piece/<slug>`, `#/piece/file` (a dropped file; not restorable after a reload, so it falls back to `#/`). Browser back and forward work.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Engine worker       | `src/engine/engine.worker.ts`, `handlers.ts`, `client.ts` | Parses MusicXML (and `.mxl`, UTF-16 and Latin-1 files, decoded once on load; the decoded text's XML declaration is rewritten to say UTF-8, so the export, saved as UTF-8, declares what it is), imports a MIDI file (`.mid`, `.midi`) as generated two-staff MusicXML with `importMidi` (M6; the import facts travel with the score as `midiInfo`), solves the fingering with `solveFingering(score, { profile })`, and writes the fingered MusicXML for export, all off the main thread. Requests carry ids so answers can arrive in any order. A worker that fails rejects every pending call and is replaced for the next piece. The app uses only the engine's public API (`@digitus2/engine`, aliased to `packages/engine/src`).                                                                                                                                                                                                                  |
| Renderer            | `src/score/render/`                                       | Verovio 6.3 (WASM) in its own worker lays the fingered MusicXML out as SVG pages. Only the newest render request counts (a resize never shows a stale layout); the width is bucketed by 160 px so small resizes do not re-layout. Our note ids are injected into the MusicXML first, so every SVG note carries the engine's note id; the main thread only swaps classes (cursor) and patches digit text (re-solve). The library page warms the worker up when idle. A worker that fails (its chunk did not load, it crashed) rejects every pending render, so the score shows an error with a way back instead of "Preparing the score…" for good; the next piece gets a fresh worker.                                                                                                                                                                                                                                                                 |
| Open pipeline       | `src/score/useScoreDocument.ts`                           | load, then solve, then fingered XML with ids, then render, as a status machine (`loading`, `fingering`, `rendering`, `ready`, `error`; `idle` is reserved and never set). The status line paints before the solve starts; an unreadable file ends in a readable error with a way back (one plain sentence, then the engine's message as the detail). A hand-size change re-solves and patches only the digits that changed. For a MIDI file, a change of the `Hand split` control opens the same bytes again with the chosen split (or without one for `Automatic`), through the same statuses; the previous import (pages, import facts, the control and its focus) stays on screen until the new one replaces it. The fingered text is kept per fingering, so a new width, or switching back to a fingering shown before, only lays it out again (writing a fingering into the MusicXML is the slowest step of an open, see the performance budget). |
| Audio               | `src/audio/`                                              | smplr's Splendid Grand Piano (public-domain samples, one velocity layer, only the piece's pitches) driven by our own look-ahead scheduler (`transport.ts`: 150 ms look-ahead; tempo, seek, loop, hand muting, metronome, count-in). The cursor is clocked by `audibleTime(ctx)` (`clock.ts`), which maps `AudioContext.getOutputTimestamp()` to what is leaving the speakers now, so the cursor stays in sync on devices with output latency (Bluetooth adds 150 to 250 ms).                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Cursor and keyboard | `src/score/useCursor.ts`, `Keyboard.tsx`                  | A `requestAnimationFrame` loop finds the onset group the listener hears and moves the red class to its notes (no animation), scrolls the sheet when the cursor changes system, and presses the keys with their finger numbers. A keyboard wider than its column scrolls sideways inside itself and follows the pressed keys in a layout effect, in the same frame as the keys change.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Design system       | `src/design/`                                             | `tokens.css` holds every color (black, white, grays and the one red, used only by `.is-red`); `base.css` holds layout, the focus ring and the print stylesheet; transitions are 120 to 200 ms ease-out and drop to 0 under `prefers-reduced-motion`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

Why Verovio (spike sections 1, 3 and 9): it keeps MusicXML note ids, so after our ids are injected every SVG note has the engine's id; it writes each digit's note into the SVG (`g.fing[data-startid]`), so one note or one digit can be made red with CSS; it honors the fingering placement per voice; and it reflows cleanly at 360 px. OpenSheetMusicDisplay, the fallback, is faster and smaller but loses on fingering engraving, per-note styling (grace notes inherit the color) and stable ids. Verovio's costs are 2.3 MB gzip (kept out of the first load as a lazy worker chunk), about 0.7 s of layout for 120 bars, and the LGPL-3.0-or-later licence (shipped unmodified as its own chunk and credited on the about page). Sources: [Verovio](https://www.verovio.org/), [smplr](https://github.com/danigb/smplr), [`AudioContext.getOutputTimestamp()`](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/getOutputTimestamp).

## The red element rule

The design brief allows black, white, grays and exactly one red (`#e3000f`), and exactly one red element on screen at a time. The definition every test uses:

- A **red root** is a visible element (not `display: none`, `visibility: hidden` or `opacity: 0`, and not inside such an element) whose own computed `color`, `background-color`, `border-*-color`, `outline-color`, `fill` or `stroke` equals `rgb(227, 0, 15)`, and whose ancestors are not red roots. Descendants of a red root are not inspected (a white label on a red button is one red root).
- A state passes when there is exactly one red root, **or** when every red root is an SVG `g.note` or `g.chord` inside `.score-sheet` and all of them carry the same `data-onset-tick` value (the playback cursor lights every note that starts at that instant, in both hands; that is one cursor).
- Which element is red, by state: library: the "Start with …" button. Score, stopped or paused: the Play button. Score, playing: the cursor notes. About: the "Back to the library" button. Error states: the "Back to the library" button. The drop zone, the notice, hover and focus states, pressed keys and finger digits are never red.

Three enforcement points:

1. `scripts/check-colors.mjs` (the `design` step of `pnpm verify`): no color literal in `apps/web/src` or `index.html` outside `tokens.css`, no second chromatic color in `tokens.css`, and the red referenced only by `.is-red`.
2. `apps/web/e2e/helpers/red.ts`: `expectOneRed(page)` applies the definition above in the browser; `e2e/states.spec.ts` runs it in every application state on desktop and at 360 px, and the flow specs run it at their own checkpoints.
3. Testing Library assertions in the component tests: the library and about views render exactly one `.is-red` element (the right button), the transport's Play button carries it while stopped and not while playing, and `Button`, `Keyboard` and the renderer's `dom` helpers have their own checks.

## Running

| Command                               | What it does                                                             |
| ------------------------------------- | ------------------------------------------------------------------------ |
| `pnpm --filter @digitus2/web dev`     | Vite dev server with hot reload.                                         |
| `pnpm --filter @digitus2/web build`   | Production build into `apps/web/dist` (with `dist/.vite/manifest.json`). |
| `pnpm --filter @digitus2/web preview` | Serves the build on port 4173, the port the Playwright suite uses.       |

Add `?audio=silent` before the hash (for example `/?audio=silent#/piece/twinkle-twinkle-little-star`) to play with a silent instrument: no sample download and no sound device needed.

**Visual baselines.** `visual.spec.ts` screenshots every state except score-playing (full page, animations disabled, the solve and layout timings hidden) and compares with the PNGs in `apps/web/e2e/visual.spec.ts-snapshots/` (named `<state>-visual-win32.png` on Windows; each under 300 KB). The `visual` project is not defined under CI, because fonts and antialiasing differ between machines. After an intended visual change, look at the failing diff in `apps/web/test-results/`, then rewrite the baselines and review the new PNGs before committing them:

```bash
pnpm --filter @digitus2/web build
pnpm --filter @digitus2/web exec playwright test --project=visual --update-snapshots=all
```

(`--update-snapshots` alone rewrites only the baselines that no longer match.)

**The silent instrument and the test hook.** With `?audio=silent` the app uses `createSilentInstrument()` (`src/audio/instrument.ts`) and installs `window.__digitus2` (`src/score/useCursor.ts`) with `positionSec()` (the transport clock), `cursorSec()` (the start of the group the cursor marks) and `groupSecs()` (every onset group's start); `playback.spec.ts` uses it to check that the cursor marks the group being heard. The hook exists only in silent runs.

Sizes are in KB of 1024 bytes, as `check-bundle-size.mjs` prints them (Vite's build log uses 1000). Solving and layout take about 0.36 s of the 2.4 s K.545 open. The app writes each fingering once per open piece and keeps the text, so a resize or switching back to a fingering shown before skips it; exporting still pays it once. Each measurement opened the piece from the library right after it rendered, in a fresh browser context, so Verovio's warm-up had little head start (waiting 3 s on the library first does not change the open time, so the warm-up is not on the critical path).

## Known limitations in this milestone

- Repeats are not expanded: playback and the cursor follow document order.
- MIDI files are imported (M6): quantized per beat to 16th notes, 16th-note triplets or 32nd notes; one voice per hand; the hands separated automatically by a learned pitch-trajectory DP, which put 92.05 percent of notes in the correct hand on the PIG test split and 85.10 percent on the Mutopia test half (macro means; scorecard m6-hands, `benchmarks/history.md`), with the `Hand split` control as the override; hands crossed at one instant always go by pitch; performance recordings without a tempo map are placed on a 120 quarter-note-per-minute grid.
- Fingerings cannot be edited or pinned yet, and there are no explanations or confidence marks (M5).
- Every note's digit is printed; the readability reduction (print only the fingers a reader needs) is M5.
- Settings persist across visits, but nothing per piece does (no saved edits, no saved loop or position).
- A dropped file cannot be restored after a reload (`#/piece/file` falls back to the library).
- The hand-size profiles use the engine's rule weights; learned weight sets (and the beginner and expert profiles) arrive with M3.
- Piano samples load from smplr's hosted sample site on the first Play; self-hosting them is a later task (spike section 9).
- A long piece opens in a few seconds (K.545: 2.4 s), most of it the engine writing the fingering into the MusicXML; the status line shows meanwhile. Exporting a long piece takes about as long.

## Interfaces beyond the plan

What the code exports or does beyond the File Structure and Interfaces blocks of the M4 plan (its "Deviations recorded during M4-A" covers Tasks 0 to 3, 5 and 7; this list covers the rest and the review fixes):

- `PressedKey.finger` is `Finger | null`: the editor's fingering is often sparse, and a pressed key without a digit still shows as pressed.
- `Playback.loading` (required): true while the samples load after the first Play; Play is unavailable and busy meanwhile.
- `ScoreDocument.digitChanges`: the digits a re-solve changed, for the view to patch in place.
- `WorkerLike` lives in `src/engine/client.ts` with an optional `onerror`; `renderer.ts` re-exports it. `createEngineClient(worker?, onFail?)` and `createRenderer(worker?, onFail?)` tell their owner once when the worker fails, and `services` in `useScoreDocument.ts` then makes a fresh one for the next piece.
- New exports: `warmUpServices`, `bucket`, `WIDTH_BUCKET_PX`, `rekeyByIndex`, `diffDigits`, `fileIdentity` (`useScoreDocument.ts`; `App.tsx` keys the score view on `fileIdentity` too), `hasNotesFor` (`onsetGroups.ts`), `mutedHandsFor` (`usePlayback.ts`), `declareUtf8` (`handlers.ts`), `messageOf` (`src/app/errors.ts`), `useFocusOnArrival` (`src/app/focus.ts`), `keysToShow` and `keyboardRange` (`Keyboard.tsx`).
- The width `ResizeObserver` is `useElementWidth` in `ScoreView.tsx` (it measures the score column), not in `ScoreSheet.tsx` as the File Structure says.
- `DocStatus` `'idle'` is reserved and never set; `reRender()`, `currentGroup`, `noteIdAt` and `OnsetGroup.endSec` have no consumer in the app yet and are kept for M5 (editing and explanations).
- `SidePanel` takes the open `source` as a prop.

## What the daily UI review should look at

Verification spec 3.10 asks for a daily qualitative review by an independent subagent, which writes `docs/reviews/ui-YYYY-MM-DD.md` and never edits product code. For this app it should, as a beginner would: open the start-here piece and one level 3 piece, read the fingering (are the digits legible, next to the right notes, not colliding with other marks), play with the cursor and the keyboard (does the cursor match what is heard, are the pressed keys and their finger numbers readable on a phone), change the hand size and switch the editor's fingering on and off, loop two bars, drop a MusicXML file and a MIDI file, export, print, and read the about page. On every screen: is the next step obvious, is exactly one thing red, is anything cluttered or ambiguous, and what would a piano teacher object to. The automated checks above cover the one-red rule, accessibility and layout overflow; the review covers what they cannot judge.
