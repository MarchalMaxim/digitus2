# Optional PC worker proof — 2026-10-15

Codex — Astra acceptance/orchestration, Sol 6.1 end-to-end implementation and verification.

An optional Python loopback worker now connects the existing deployed GitHub Pages frontend to the checked portable Audiveris recognizer. No product scan UI, public listener, external recognition service, installation or autostart is added. This is a real HTTP/native-process/browser proof, not a mocked recognizer demonstration. Recognition always remains `needsReview`; an HTTP success certifies completion/transport only.

## Actual deployed-origin result

Disposable installed Chrome 155 contexts visited `https://marchalmaxim.github.io/digitus2/`. With the granular loopback permission denied, fetch failed. With it granted, the reusable browser client reached the worker, uploaded original clean Twinkle PNG bytes, polled the asynchronous job, received untouched exported MusicXML, and explicitly opened that raw result using the existing frontend import. The frontend rendered SVG notation with 64 fingering groups and an enabled Play button. No playback-tempo correctness is claimed.

The final reviewed-source run with explicit short-staff profile plus pinned English model took approximately 5.06 seconds from browser submission through result receipt. The native process took approximately 4.95 seconds; the earlier matching run measured 4.70/4.64 seconds. Strict single-fixture evaluation recovered 64/64 notes, 12/12 bars, zero bar timing mismatches and full-note F1 100%. This is one clean development fixture, not a corpus-wide accuracy estimate. Held-out quality findings remain in the separate quality report. In particular, OCR can recover “= 100” as words without resolving a metronome beat unit or reliable playback BPM.

A second actual native job was cancelled after submission: it exited nonzero in approximately 0.34 seconds, reached `cancelled`, and its result endpoint returned 409. Process records and actual isolated AppData/tessdata paths are retained locally. No partial output was published. Generic lifecycle tests additionally kill a real Python child and descendant on cancellation and timeout; these tests establish lifecycle behavior, not recognition accuracy.

Final evidence is ignored under `research/omr/results/connector-wave/browser-reviewed-eng/`: `report.json`, raw `twinkle-twinkle-little-star.musicxml`, `strict-single-fixture.json`, the actual frontend screenshot, and per-job invocation/process/native logs. Those four recorded operational source hashes identify the executed pre-metadata-fix files. The final review added only structured OCR-configuration warnings/capabilities and an explicit English-model provenance hash; focused tests cover those additions, and `final-reviewed-source-hashes.json` records the final reviewed files. The raw recognition proof is not relabelled as execution of that later metadata revision. Initial permission experiments are preserved under `browser-origin-1/2`; their failed connection was not hidden or described as success. Earlier successful runs retain their own raw outputs. ## Browser permission and boundaries

[Chrome's local-network permission description](https://developer.chrome.com/blog/local-network-access) explains that a public HTTPS origin needs permission to reach a companion program on loopback. The actual Chrome 155 test also exposed the newer split described in [Google Chrome's guidance](https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/security/local-network-access.md): `loopback-network` governs this endpoint. A legacy `local-network-access` grant alone still produced a loopback-permission denial. The successful client declares `targetAddressSpace: 'loopback'`. No unsafe browser flag, OS security change or real-user profile modification was used; CDP only set permission states in fresh disposable contexts. This does not claim that a human permission-prompt interaction was tested or that every browser supports the same path.

The server binds only IPv4 loopback and validates the exact Host/port and allowed HTTPS Origin before handling requests. Mutations also require the explicit client header; preflight headers are allowlisted. There is no cookie authentication, wildcard CORS, filename-controlled executable, user-provided command, shell invocation, result-path endpoint or public bind option. The allowed GitHub Pages origin is shared by that account's project paths; origin checks cannot distinguish individual projects under it, nor authenticate against an already-running local program that can forge headers.

One native job runs at a time. Request-handler count, upload/result sizes, job count, retention and process time are bounded. Source bytes are stored under opaque server-owned job directories. Direct argv uses the pinned portable Java/classpath, job-specific settings/home/temp/native cache and optional copied checked OCR data. Inherited JVM agent/options and OCR paths are removed. Cancellation and timeout stop the owned native process tree before a terminal job state is published. Results are released only after successful exit, one unambiguous contained export, bounded decompression and XML parsing; this does not mean the recognizer recovered every source event correctly. Exceptions expose generic error codes rather than local paths.

The native heap cap and sampled log/workspace guards are not an OS sandbox or a hard native-memory quota. The standalone worker requires deliberate startup, a maintained trusted portable toolchain and normal Ctrl+C shutdown. Expired interrupted jobs with owned markers are cleaned when the worker runs; unrelated files are preserved. It is not a public/VPS deployment design: authentication, TLS, multiuser isolation, process supervision and deployment policy would need separate work before changing the listener boundary.
