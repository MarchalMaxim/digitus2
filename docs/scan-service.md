# Scan service

Scanning (`docs/scanning.md`) sends each page to a small recognition service that the project runs on Google Cloud Run. It is the one server the product has: the app itself stays a static site on GitHub Pages, and the engine runs in the browser. This document says what runs where, how the app talks to the service, how it is configured and deployed, what it costs and how its spend is capped. The design and the routes weighed are in `docs/superpowers/specs/2026-10-19-scan-service-design.md` and `docs/research/omr.md` (Hosted recognition); the commands in full are in `research/omr/service/README.md`.

## What runs where

| Part                             | Runs                                                                                                  | Code                                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| The app, the review, corrections | The reader's browser, served by GitHub Pages                                                          | `apps/web/src/scan/` (`client.ts` speaks the protocol below, `ScanView.tsx` the scan page)          |
| The service's address            | Built into the app                                                                                    | `apps/web/src/scan/service.ts`; `VITE_SCAN_SERVICE` names another for development and the e2e specs |
| Recognition                      | One container on Cloud Run, region `europe-west4` (Netherlands), project `digitus2-scan`              | `research/omr/service/` (`service.py`, `Dockerfile`, `setup-homr.py`)                               |
| Photos (PNG, JPEG)               | homr at the pinned commit with the patches listed in `homr-photo/README.md` and its three ONNX models | the adapter `research/omr/prototypes/local-worker/homr.py`                                          |
| PDFs                             | Audiveris 5.11.0 from its Ubuntu 24.04 package, short-staff profile, English text model               | the adapter `research/omr/prototypes/local-worker/audiveris.py`                                     |
| Spend control                    | A budget on the billing account and a Cloud Run function in the same project                          | `research/omr/service/budget/`                                                                      |
| My scores                        | The reader's browser (IndexedDB); nothing is stored on the service                                    | `apps/web/src/library/local/`                                                                       |

The container holds everything a recognition needs and fetches nothing at run time. When the image is built, the base image is pinned by its digest, and these downloads are checked against a pinned SHA-256: the Audiveris package, the homr source archive at its pinned commit, homr's three ONNX models, and the English text model with its licence. The Python wheels are pinned by version only, because the locked requirements carry no hashes, and the system packages are the Ubuntu 24.04 archive's current ones at build time (`research/omr/service/README.md`, Build). The service reuses the research worker's job runner, adapters, export rules and error mapping (`research/omr/prototypes/local-worker/`), so the hosted pipeline and the acceptance gate's pipeline are the same code.

## Protocol `digitus2-scan-v2`

The recognition happens inside one request, because Cloud Run bills and runs the CPU only while a request is in flight. Every request needs exactly one `Origin` from the allowlist: `https://marchalmaxim.github.io`, plus loopback development origins passed with `--dev-origin`. POST and DELETE also need `X-Digitus2-Client: 1`. These checks stop casual scripts; they are not authentication, and no secret ships in the static app.

| Request                                                                                                                                                            | Answer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/health`                                                                                                                                                   | 200 `{"protocol":"digitus2-scan-v2","needsReview":true,"recognizer","capabilities","warnings","maxUploadBytes":10485760,"threads":4}`; `threads` is the recognisers' thread budget, `null` when none applies. Static: it loads no model.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `POST /v1/recognize`, `Content-Type` `image/png`, `image/jpeg` or `application/pdf`, `X-Digitus2-Job: <32 lowercase hex chosen by the client>`, the original bytes | 200 `{"state":"ready","needsReview":true,"recognizer","capabilities","warnings","xml"}`. 422 `{"state":"failed","failure":{"code","message","details"}}`. 504 `{"state":"timed_out","failure"}` after 180 s. 409 `{"state":"cancelled"}` after a cancel, or `{"error":"duplicate-job"}` for an id already running. 429 `{"error":"busy"}` with `Retry-After: 30` while another recognition runs; 429 `{"error":"rate-limited"}` with `Retry-After` the seconds until the caller's oldest recognition leaves the hour. 400 without a valid job id, 403 for a missing origin or client header, 408 when the upload stalls, 411 without one plain `Content-Length`, 413 over 10 MiB, 415 for another type, a compressed body or bytes that do not start like the declared type. |
| `DELETE /v1/jobs/<id>`                                                                                                                                             | 200 `{"id","state":"cancelling"}`: the native process tree is killed and the pending POST answers 409. 404 for an unknown or finished id.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `POST /v1/cases/<scan id>`, `Content-Type: application/json`, what the review said (Validation cases, below)                                                       | 204 kept. 404 when the service has no cases bucket or the scan id is not one this instance kept in the last hour; 400 for a body that is not a JSON object, 413 over 64 KiB, 415 for another type, 429 after 100 reviews of a scan.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `OPTIONS`                                                                                                                                                          | 204, the CORS preflight for the allowed origins: methods GET, POST, DELETE; headers `Content-Type`, `X-Digitus2-Client`, `X-Digitus2-Job`, `X-Digitus2-Keep`, `X-Digitus2-Page`; `Access-Control-Max-Age: 86400`, so a browser keeps it (Chrome for at most two hours) instead of asking before every page.                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

The client chooses the job id so that **Cancel scan** can name a job whose answer has not arrived. Every answer carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. The app waits at most 200 s for a recognition (`client.ts`), above the service's own 180 s limit, so the service's 504 normally answers first. A busy or duplicate answer does not count against the caller's hourly limit, because no recognition started. The app offers a busy job again every 5 s for up to three minutes. The service does not expose `Retry-After` to the browser (no `Access-Control-Expose-Headers`), so the 5 s floor applies.

## Limits and boundaries

| Limit                         | Value                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Recognitions at once          | 1 per instance, and at most 1 instance                                                                                                                                                                                                                                                                                                                             |
| Recognitions per caller       | 30 in a rolling hour, kept in memory and reset when the instance stops                                                                                                                                                                                                                                                                                             |
| Caller                        | The last address in `X-Forwarded-For`, the one Google's front end appends (a client can forge the earlier ones), or the socket address                                                                                                                                                                                                                             |
| Upload                        | 10 MiB, checked for size, type and leading bytes before the job starts                                                                                                                                                                                                                                                                                             |
| Result                        | 20 MiB of MusicXML                                                                                                                                                                                                                                                                                                                                                 |
| Recognition time              | 180 s, then 504                                                                                                                                                                                                                                                                                                                                                    |
| Thread budget                 | homr's ONNX Runtime and OpenCV use as many threads as the container's CPU quota (4 at `--cpus 4`), not the host's cores (the libraries' own defaults without a quota); `DIGITUS2_OMR_THREADS` or `--threads` sets it. Cloud Run does not expose its 4 vCPU allotment that way (the service detected 9), so the deploy sets `DIGITUS2_OMR_THREADS=4` on the service |
| Image size                    | homr refuses images over 25 megapixels                                                                                                                                                                                                                                                                                                                             |
| What is kept after the answer | Nothing, unless the device opted in and the service has a cases bucket: then the page, its recognition and what the review said, in a private bucket for 365 days (Validation cases, below). Otherwise each job has its own temporary directory, deleted before the answer is sent; no job list, no result, no copy of the page                                    |
| Log                           | One JSON line per job on standard output: file kind, bytes in, bytes out, seconds, outcome. No content, no file name, no address                                                                                                                                                                                                                                   |
| Network during a job          | homr runs with Python's socket functions disabled by the adapter; the Audiveris JVM is not restricted; no network-level isolation is built                                                                                                                                                                                                                         |

Cloud Run writes its own request log for the service in Cloud Logging, as for every Cloud Run service; that log is Google's, not the service's ([Cloud Run logging](https://cloud.google.com/run/docs/logging)).

## Validation cases

A device can opt in to keeping its scans as validation cases (issue 233), so that a scan that went wrong on a phone can be replayed on the owner's PC. Nothing is kept unless both hold:

| Condition                | How                                                                                                                                                                                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The device opted in      | Opening the app at `…/#keep-scans` turns it on for that browser (`localStorage`, `apps/web/src/scan/diagnostics.ts`); `…/#keep-scans-off` turns it off. The address returns to where it was, without a history entry; nothing else on screen changes |
| The service has a bucket | The environment variable `DIGITUS2_CASES_BUCKET` names it; `deploy.ps1` and the GitHub Action set `digitus2-scan-cases`. Without it the service keeps nothing, whatever the device sends                                                             |

While both hold, every recognise request of the device carries `X-Digitus2-Keep: <scan id>` (the scan's session id as 32 lowercase hex), and `X-Digitus2-Page: <page id>` (the page's id, also as 32 lowercase hex) when the app names the page. The service keeps them under `cases/<UTC date>/<scan id>/<visit>/` in the bucket. A visit is the stretch in which the service remembers the scan (below); it is named by the time, in milliseconds since 1970, of its first page, and the date is that page's, so a scan across midnight stays together and a scan that comes back never reuses a name. Each visit folder holds:

| Object                           | What it is                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `page-<n>.jpg`, `.png` or `.pdf` | The upload as sent; `n` counts the visit's pages in the order they reached the service, a retaken page or a page sent again included                                                                                                                                                                                                                |
| `page-<n>-id.json`               | `{"page": "<page id>"}`, when the request named the page: a retaken page has a new id, a page sent again keeps its id                                                                                                                                                                                                                               |
| `page-<n>-recognized.musicxml`   | The recognised MusicXML, when the recognition produced one                                                                                                                                                                                                                                                                                          |
| `page-<n>-recognition.json`      | homr's `recognition.json` (its warnings and audit), for a photo                                                                                                                                                                                                                                                                                     |
| `review-<k>.json`                | What the review told the reader (`ReviewFacts`, `apps/web/src/scan/facts.ts`): the verdict, whether Use for fingerings was available, the alert, the Technical reason lines, the places to check, the page named, the number of corrections. The app sends each change, one after the other in the order it happened; the highest `k` is the latest |

A page is kept only once its recognition has started: a busy, duplicate, rate-limited or refused offer keeps nothing. A malformed `X-Digitus2-Keep` keeps nothing and changes nothing else. `POST /v1/cases/<scan id>` takes `application/json`, an object of at most 64 KiB, for a scan this instance kept a page or a review of in the last hour, at most 100 times a scan.

| Property           | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bucket             | `gs://digitus2-scan-cases`, project `digitus2-scan`, region `europe-west4`; uniform bucket-level access, public access prevention                                                                                                                                                                                                                                                                                                                     |
| Retention          | A lifecycle rule deletes each object 365 days after it was written                                                                                                                                                                                                                                                                                                                                                                                    |
| Who writes         | The service's account `digitus2-scan-run`, with `roles/storage.objectCreator` on this bucket only: it can add objects, never read, list, replace or delete them, so code reached through a recogniser that takes its token can do no more. Uploads use the JSON API with `ifGenerationMatch=0` and a token from the metadata server; no Python dependency is added                                                                                    |
| Who reads          | The owner's account (`roles/storage.objectViewer`)                                                                                                                                                                                                                                                                                                                                                                                                    |
| When it is written | Cloud Run gives an instance CPU only while a request is in flight, so every write happens inside one. The upload is written in a background thread when its recognition starts; the MusicXML and `recognition.json`, also in background threads, when it ends, and the answer waits up to 2 s more for them. A review waits up to 5 s for its scan's writes still under way, then writes itself before it answers. The reader never waits on a review |
| A failed write     | Logged to standard error as one JSON line (`keepFailed` with the object's file name, the error's type and status) and ignored                                                                                                                                                                                                                                                                                                                         |
| Cost               | Cloud Storage Standard in `europe-west4`, about 0.02 USD per GB a month ([pricing](https://cloud.google.com/storage/pricing)); a case is a few megabytes                                                                                                                                                                                                                                                                                              |

The scan ids the service knows are kept in memory: a review after the instance stopped, or more than an hour after the scan's last page or review, is refused with 404. A scan that sends pages again after that starts a new visit, counted from `page-1`, in a folder of its own.

To set the bucket up, once, before the first deploy that names it (from the owner's machine; it creates nothing else and deploys nothing):

```powershell
powershell -File research/omr/service/setup-cases.ps1 -Reader OWNER@EXAMPLE
```

To turn keeping off for a device, open `…/#keep-scans-off` on it. To turn it off for every device, deploy with `-CasesBucket ''` (`deploy.ps1`) and remove `CASES_BUCKET` from the workflow; the cases already kept stay until the lifecycle deletes them, or are deleted in the console.

To replay the cases on the PC, copy them into the validation store named by `DIGITUS2_SCAN_CASES` (the owner's is `C:/Users/maxim/omr/scan-cases`; never committed):

```powershell
gcloud storage rsync -r gs://digitus2-scan-cases/cases $env:DIGITUS2_SCAN_CASES
```

Each `<date>/<scan id>/<visit>/` folder is then a case: `page-N` with `page-N-recognized.musicxml`, as the app's Download everything archive also writes. A scan whose pages were retaken, sent again after a refusal, reordered or removed holds more pages, or another order, than the reader saw. Its `page-N-id.json` group the uploads of one page that was sent again; a retaken page has a new id, so telling it from an added page needs the order of the pages on screen, which the review does not report.

## Cloud Run configuration

| Setting                 | Value                                | Why                                                                                                                |
| ----------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Project, service        | `digitus2-scan`, `digitus2-scan`     | A project of its own, because the kill-switch disables billing for a whole project                                 |
| Region                  | `europe-west4` (Netherlands)         | Tier 1 price                                                                                                       |
| Billing                 | Request-based (the default)          | CPU and memory are billed only while a request is being handled                                                    |
| CPU, memory             | 4 vCPU, 8 GiB                        | homr's segmentation uses the cores; Audiveris keeps its 4 GiB heap; memory is cheap next to CPU                    |
| Concurrency             | 4                                    | One recognition at a time inside the service; health, cancel and busy answers still get through                    |
| Minimum instances       | 0                                    | Scale to zero: no idle charge                                                                                      |
| Maximum instances       | 1                                    | Bounds the worst case to one busy instance                                                                         |
| Request timeout         | 240 s                                | Above the 180 s recognition limit                                                                                  |
| Startup CPU boost       | On                                   | A shorter cold start                                                                                               |
| Execution environment   | Second generation                    | Full Linux for the JVM and the native libraries                                                                    |
| Ingress, authentication | All, unauthenticated                 | The app is a public static site                                                                                    |
| Port                    | 8080 (`PORT`)                        | The service listens on `0.0.0.0` and the port Cloud Run gives it                                                   |
| Service account         | `digitus2-scan-run`, no project role | Its logs go through standard output; its one Google API is creating objects in the cases bucket (Validation cases) |

**Warm-up instead of keep-warm.** When the scan page opens, the app sends one `GET /v1/health` and keeps only the capabilities from the answer. That starts an instance while the reader arranges pages, so **Scan this score** usually finds it running. One request per visit to the scan page, never from the library. There is no periodic ping and no minimum instance: a ping every 10 s would bill at least 100 ms of the whole instance each time, about 104,000 of the 180,000 free vCPU-seconds a month.

## Deploy

From the owner's machine, with gcloud installed and signed in, from the repository root:

```powershell
powershell -File research/omr/service/deploy.ps1 -Project digitus2-scan
```

`deploy.ps1` enables the Cloud Run and Artifact Registry APIs, builds the image, pushes it to the Artifact Registry repository `digitus2` (a cleanup policy keeps the most recent version and the one tagged `live`, which the deploy gives the serving image after the smoke test), deploys it with the settings above, prints the service URL and runs `research/omr/service/smoke.mjs` against it: one phone photo and one corpus PDF, each of which must come back as a ready `score-partwise` document. It is safe to run again, and it is how the service comes back if Google removed it. The image is tagged with the short git commit, with `-dirty` when `research/omr` has uncommitted changes.

The deployed URL has Cloud Run's fixed form, `https://digitus2-scan-<project number>.europe-west4.run.app`, and goes into `apps/web/src/scan/service.ts`. GitHub Pages deploys every push to `main`, so an app change that needs a new service ships only after the service is deployed; a merge that changes the service deploys it (below).

### Deploying on merge

The GitHub Action `.github/workflows/scan-service.yml` runs on a push to `main` that changes `research/omr/service/`, `research/omr/prototypes/homr-photo/`, `photo-recovery/` or `local-worker/`, `research/omr/.dockerignore` or the workflow itself, and on demand. It builds the image as `deploy.ps1` does, pushes it tagged with the short commit, deploys a revision with the same settings but no traffic under the tag `candidate`, runs `smoke.mjs` against the tagged URL (one photo, and `aot-training.pdf` for the PDF route), and only then moves the traffic to the smoked revision by name, removes the tag and tags the image `live`. A failed smoke fails the job and the previous revision keeps the traffic. Authentication is keyless: GitHub's OIDC token is exchanged through Workload Identity Federation for the service account `digitus2-scan-deploy`, which accepts runs on `main` of this repository (pushes and manual runs) and holds Cloud Run Developer on the project, Artifact Registry Repository Administrator on the repository (moving the tag `live` deletes it from the previous image, which a writer may not do) and Service Account User on the run account. The job is skipped while the repository variable `SCAN_DEPLOY_PROVIDER` is empty. The Action updates an existing service: the first deploy, and the way back after Google removed the service, is `deploy.ps1`. The owner runs `powershell -File research/omr/service/setup-github-deploy.ps1 -Project digitus2-scan` once, after `deploy.ps1` has run; it creates the account, pool and provider, sets the cleanup policy to keep the newest image and the `live` one (the same image except after a failed smoke) and sets the variables `SCAN_DEPLOY_PROVIDER` and `SCAN_DEPLOY_ACCOUNT`.

| Item                                   | Cost                                                                                                                                                                                                                                                                                            |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Image in Artifact Registry             | About 0.7 GB (690 MB measured in the registry); the first 0.5 GB a month is free, then 0.10 USD per GB a month ([pricing](https://cloud.google.com/artifact-registry/pricing)); with the kill-switch's function images (0.05 GB) about 0.03 USD a month with the newest and the live image kept |
| GitHub-hosted runner                   | Free minutes for public repositories ([billing](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions))                                                                                                    |
| Workload Identity Federation           | Free                                                                                                                                                                                                                                                                                            |
| Smoke (about 50 s, one photo, one PDF) | Inside Cloud Run's free grant                                                                                                                                                                                                                                                                   |

Before a deploy, the image is built and checked locally (`research/omr/service/README.md`, Build and Run locally), and the acceptance gate runs against the running container (`node research/omr/acceptance.mjs --service URL`; `docs/research/omr.md`, Hosted recognition).

## Budget and kill-switch

| Piece        | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Budget       | `digitus2-scan` on the billing account, 10 a month in the billing account's currency, for this project only; e-mail alerts at 50, 90 and 100 percent                                                                                                                                                                                                                                                                                                |
| Notification | The budget publishes the month's running cost to the Pub/Sub topic `digitus2-scan-budget` several times a day                                                                                                                                                                                                                                                                                                                                       |
| Kill-switch  | The Cloud Run function `stop-billing` (Python, `budget/main.py`, after Google's sample), triggered by the topic: when the notified cost reaches the budget, it unlinks the project from its billing account                                                                                                                                                                                                                                         |
| Identity     | Its own service account with Billing Account Administrator on the billing account, as Google's guide grants; its code unlinks only its own project. The scan service runs as `digitus2-scan-run@<project>.iam.gserviceaccount.com`, an account with no project role, which may only create objects in the cases bucket (Validation cases); the Compute Engine default account, which holds Editor on a project without an organization, is not used |
| Set up with  | `powershell -File research/omr/service/budget/budget.ps1 -Project digitus2-scan -BillingAccount ID`, first in simulation mode, tested with a published notification over the budget, then redeployed with `-Simulate false` (`research/omr/service/README.md`, Budget and kill-switch)                                                                                                                                                              |

This follows Google's [Disable billing usage with notifications](https://docs.cloud.google.com/billing/docs/how-to/disable-billing-with-notifications). Billing notifications lag by hours, so the real ceiling is 10 plus what a busy instance costs during the lag: at the worst case below, about 10 a day, a lag of, for example, six hours adds about 2.50.

## When billing is disabled

When the kill-switch fires, the service stops answering and the app says "The scanner could not answer. Try again later." Google's own answer in front of the service carries no CORS header, so the browser reports it as a network error, without a status; the app tells it apart from an offline device by `navigator.onLine` (`apps/web/src/scan/client.ts`). Scanning stays off until the budget period resets on the first of the month: the notifications repeat with the month's running total, so a project relinked while the total is above the budget is unlinked again within hours. Nothing resumes automatically.

To recover, on the first of the month, or after raising the budget for the current month (Billing, Budgets & alerts, the `digitus2-scan` budget), link the project to the billing account again in the Cloud console (Billing, My projects). The service resumes by itself; if Google removed it meanwhile, run `deploy.ps1` again. Unlinked billing can also shut down or delete the kill-switch function, and a relinked project without it has no ceiling, so check it after relinking and run `budget.ps1 -Simulate false` again if it is missing or still simulating (the check command is in `research/omr/service/README.md`, When billing is disabled).

## Timings

The photo is the owner's flat phone photo of Boëllmann Op. 28 No. II, page 5 (`research/omr/photos/boellmann-op28-page5-flat.jpeg`, 153,687 bytes); the PDF is the acceptance corpus's Amazing Grace (`amazing-grace/clean.pdf` rendered by `research/omr/prepare.mjs`, 51,425 bytes). Times are the whole request as `smoke.mjs` measures it. The container rows are one session at 4 vCPU and 8 GiB: a fresh container per round, one image at a time, the two images alternating, two requests each. A container time is the median of the six requests of the three rounds the PC was otherwise idle (photo 7.8 to 9.5 s against 9.4 to 19.1 s, PDF 6.1 to 6.4 s against 8.1 to 13.3 s); in the other three rounds other work slowed both images alike. First and later requests take the same time. The speed changes (Audiveris without `-save` and with an ahead-of-time class cache, and two homr patches) leave every output of the acceptance gate unchanged; `docs/research/omr.md`, Scan speed.

| Where                                                                             | Health from a cold service (cold start) | Photo (homr) | PDF (Audiveris) |
| --------------------------------------------------------------------------------- | --------------------------------------- | ------------ | --------------- |
| The container on the owner's PC at 4 vCPU and 8 GiB                               | —                                       | 8.5 s        | 6.3 s           |
| The container without the speed changes of issue 73                               | —                                       | 11.5 s       | 9.9 s           |
| The deployed service without the speed changes, first requests after a cold start | 4.5 s                                   | 34.0 s       | 15.8 s          |
| The deployed service without the speed changes, warm                              | —                                       | 35.2 s       | 16.2 s          |

The cold start is measured from outside: a health request after 40 idle minutes, with no instance left, answered in 4.5 s, and the next one in 0.06 s. Cloud Run's own system log agrees: 3.4 to 6.3 s from each instance start to the moment the container listens, median 4.4 s, across 34 starts (below). A reader whose warm-up finds no instance waits that long before the health answer. Cloud Run's front end can also answer a request itself, with 429 when no instance is available (during a rollout, or when the one instance is saturated) or with an error once billing is disabled; those answers carry no CORS headers, so the browser reports them as a failed request and the app shows that the scanner could not answer. The container is ready about 2 s after it starts. Each Audiveris job extracts its native libraries into its own cache, so cold and warm PDF times are alike. A Cloud Run vCPU is slower than a core of the owner's PC, and the photo path suffers most: with the same thread budget of 4, a photo takes about 3.5 times longer on the service than in the container at home and a PDF page about 1.9 times. Runs on the service also vary more than at home: the same warm photo took between 24 and 36 s across one day. A thread budget of 2 on the service was tried and is slower (31 to 32 s against 24 s with 4 on the same afternoon). The stage timings behind these numbers and the options they leave are in `docs/research/omr.md`.

The app's estimate (`apps/web/src/scan/progress.ts`) errs long: the countdown already says "overdue" when a page runs past it, and a bar that finishes early costs nothing. A photo and the warm-up count the 90th percentile of their runs. A PDF page counts the slowest page rate measured, times the spread of the PDF runs. The figures are rounded up (a photo or a PDF page to 5 s, the warm-up to whole seconds).

| Part                                                 | Counted | Because                                                                                                                                                    |
| ---------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A photo                                              | 35 s    | 90th percentile: 34.2 s over every revision, 31.9 s on the current ones                                                                                    |
| A PDF page                                           | 30 s    | 24.8 s a page for the two-page PDF, the slowest page rate in the log, times 1.11, the one-page PDF's 90th percentile over its median (19.6 / 17.7): 27.5 s |
| The warm-up, while the scanner may still be starting | 6 s     | 90th percentile of cold starts: 5.4 s, 6.3 s at most                                                                                                       |

The PDF page is no percentile: the log holds 18 runs of the one-page Amazing Grace (90th percentile 19.6 s, which 35 s covers) and a single run of a multi-page PDF, the two-page Träumerei (49.5 s on the service, so 60 s counted for it). A fixed part and a per-page part cannot be told apart from two pieces of different density, so the slower page rate stands for every page, and the one-page PDF's runs give the spread. The photos' wider spread (34.2 / 25.1, 1.36) is not used: a photo goes through homr, a PDF through Audiveris. A second multi-page PDF in the log is a reason to run the same rule again, with its own percentile.
