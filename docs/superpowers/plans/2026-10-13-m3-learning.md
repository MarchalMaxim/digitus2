# M3 Learning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the rule-based solver into a learned linear model: the same exact decoder, the same named terms plus new indicator and timing features, with weights fitted on expert fingerings by a structured perceptron, calibrated confidences, a benchmark that reports paired-bootstrap confidence intervals against the strongest third-party baselines, the Mutopia editorial corpus wired in as a second oracle, a shippable weight set trained only on permissively licensed data, a beginner profile, and floors raised to the learned numbers.

**Architecture:** Every cost the solver computes is `Σ weight[rule] × points[rule]`, so a complete fingering has a feature vector Φ (points summed per rule along the path) and `cost = w · Φ`. `packages/engine/src/learn/` adds `pathFeatures` (Φ from the same `unaryTerms`/`pairTerms`/`tripleTerms` the solver uses), an averaged passive-aggressive perceptron with loss-augmented decoding through the existing `solveHand` (a new optional `unaryExtra` hook), latent targets for pieces with several annotators and for partially fingered pieces, and the calibration fit. `cli/learn.ts` loads the corpora (PIG train, textbook, Beringer, the Mutopia train half), trains, and writes a weight set with provenance. `cli/bench.ts` gains `--weights`, `--compare` (paired bootstrap against `research/baselines/results_per_piece_test.csv`), masked metrics for partially fingered gold, and the calibration row. Training runs in TypeScript, in Node, through the CLI (a deviation from the product spec's "Python harness exports learned parameters": the features and the decoder exist once, in the engine, and the Python side keeps the data, the splits and the statistics).

**Tech Stack:** as M2 (TypeScript strict, vitest, pnpm; Node only under `cli/`). Python 3.11 under `research/` for the Mutopia split script and its test.

**Spec:** `docs/superpowers/specs/2026-10-13-digitus2-design.md` sections 7.1, 7.2, 7.4; `docs/superpowers/specs/2026-10-13-verification-design.md` sections 1 (goals), 2 (oracles 1 to 5), 3.2, 3.3, 3.8, 4 (iteration protocol). Method background: `docs/research/literature.md` sections 2.11, 2.17, 6.5 (log-linear model and structured perceptron), 6.6. Data: `docs/research/datasets.md` sections 2.4, 4, 5; `docs/research/baselines.md` "What digitus2 should take from this" and the per-implementation notes on FingerFlow and chirality. ## Global Constraints

- Never tune on the PIG test split (pieces 001 to 030). Training uses PIG pieces 031 to 150 minus a fixed validation list, the textbook oracle, the Beringer corpus and the Mutopia **train** half. The Mutopia **test** half is a held-out oracle (verification spec section 4 item 5, amended by Task 2 with a dated note: Mutopia is split by piece; the test half stays held out).
- PIG is licensed for non-profit academic use. Weights fitted on PIG are research artifacts: written under `research/weights/` (gitignored), never into `packages/engine`, never into the app. The shippable set `weights-learned-open.json` is fitted only on the textbook oracle, Beringer (MIT) and the Mutopia train half (public domain, CC BY, CC BY-SA engravings; the fitted numbers are statistics about fingering practice, not copies of the engravings).
- The decoder, the rule terms and the solver's constraints are not changed except as this plan says (one optional hook in `solveHand`, new rule ids with weight 0 in the Parncutt set). With the Parncutt weight set the engine's output must stay byte-identical to M2 (`benchmarks/latest.json` numbers reproduce).
- Costs stay linear in the weights: no feature may read a weight.
- Determinism: training with the same data, seed and options produces byte-identical weight files (seeded LCG shuffles; no `Math.random`, no `Date` inside the trainer; the provenance timestamp is written by the CLI from a `--date` option or the current time, which is the only non-deterministic field).
- Speed: `solveFingering` with the learned set must still solve a 2000-note piece under 500 ms in Node (goals table); training on the full `pig` configuration must finish in under 15 minutes on this machine.
- `pnpm verify` stays green after every task; implementers do not run git (CLAUDE.md). `packages/engine/src` keeps no DOM or Node APIs.

## Review Focus

1. A weight update that uses the wrong sign makes training diverge silently (the cost of the expert fingering goes up instead of down) while the code still "runs"; pinned by Task 3 (`one update lowers the cost of the target relative to the decoded path` and `training on a toy corpus reaches 100 percent`).
2. Partially fingered Mutopia parts: a note with finger 0 is unknown, not "finger 0"; if it leaks into Φ or the Hamming loss, the open weights are trained on garbage. Pinned by Task 2 (`parsePig treats finger 0 as unfingered`) and Task 3 (`unfingered notes contribute nothing to the loss or the augmentation`).
3. Feature ids must be exactly the same strings in `RuleId`, the weight files, `pathFeatures`, the ablation table and the explanations, or a learned weight is silently ignored. Pinned by Task 1 (`every rule id produced by the term functions is a key of every weight file, and vice versa`).
4. The Parncutt set must be unaffected by the new features (all new weights 0) so M2's scorecard and goldens still hold. Pinned by Task 1 (`with the Parncutt set, textbook accuracy and the scorecard reproduce M2`).
5. The bootstrap comparison can mislead if pieces are paired wrongly (baseline rows sorted differently, or a skipped piece). Pinned by Task 5 (`pairs by piece id, fails on a missing piece, reproduces the baselines report's FingerFlow minus FHMM3 interval`).

```ts
// unary indicators (10): `on:<f>:black`, `on:<f>:white` for f = 1..5 — 1 point when finger f plays a black (white) key
// melodic transition indicators (50): `tr:<g><f>:up`, `tr:<g><f>:down` for g, f = 1..5 — 1 point for consecutive notes in different slices with b.pitch > a.pitch (up) or < (down), mirrored pitch; repeated keys (i = 0) get neither
// chord pair indicators (10): `ch:<g><f>` for g < f — 1 point for each adjacent pair inside a slice (fingers ascend with pitch, so g < f always)
// lattice (2): `latticeStep` = |Δx − (f − g)| where Δx = (x14(b.pitch) − x14(a.pitch)) / 2 in white-key units, for melodic pairs (different slices, i ≠ 0), i.e. how far the pair deviates from "one white key per finger"; `levelChange` = 1 when a.black !== b.black for melodic pairs
// timing (3): `stretchFast` = stretch points × [b.ioi < hopFastSec]; `shiftFast` = handPositionShift points × min(1, 0.25 / max(b.ioi, 0.01)) (relocation at speed); `repeatFast` = 1 when i = 0 and b.ioi < repeatFastSec regardless of fingers (lets the model learn how costly fast repeats are at all)
```

`RULE_IDS: readonly RuleId[]` (exported, sorted) lists every id, and `isPenaltyRule(id)` returns true for the physical rule terms that must stay non-negative during learning (`stretch`, `smallSpan`, `largeSpan`, `beyondPractical`, `chordStretch`, `chordSmallSpan`, `chordLargeSpan`, `chordBeyondPractical`, `hop`, `repeatedNoteSameFinger`, `handPositionShift`, `positionChangeSize`, `stretchFast`, `shiftFast`) and false for indicators, `template` and the remaining count-style rules.

**Files:**

**Interfaces:**

- Consumes: `HandExample`, `pathFeatures`, `dot`, `solveHand` with `unaryExtra` and `pinned`, `makeContext`, `RULE_IDS`, `isPenaltyRule`, `Lcg`.
- Produces:

```ts
export interface TrainOptions {
  profile: HandProfile; // spans used during training (large for PIG)
  init: RuleWeights; // starting point, usually PARNCUTT_WEIGHTS
  epochs: number; // default 12
  C: number; // PA-I aggressiveness cap, default 0.2 (prototype sweep)
  rho: number; // Hamming loss scale per note, default 1
  seed: number;
  validation?: HandExample[]; // when given, the epoch with the best validation note accuracy wins
  projectPenalties: boolean; // default true: penalty rules clamped at >= 0 after every update
  onEpoch?: (info: EpochInfo) => void;
}
export interface EpochInfo {
  epoch: number;
  updates: number;
  trainAccuracy: number;
  validationAccuracy: number | null;
  averagedWeights: RuleWeights;
}
export interface TrainResult {
  weights: RuleWeights;
  bestEpoch: number;
  epochs: EpochInfo[];
  features: RuleId[];
}
export function train(examples: HandExample[], opts: TrainOptions): TrainResult;
export function evaluateExamples(
  examples: HandExample[],
  weights: RuleWeights,
  profile: HandProfile,
): { noteAccuracy: number; notes: number }; // decode each example with solveHand (no constraints) and count notes whose finger equals ANY annotation's finger (unfingered golds skipped)
```

Algorithm, per epoch, over the examples in a seeded shuffled order:

1. `ctx = makeContext(profile, w)`.
2. **Target.** Pick the reference annotation `k*` = the annotation whose fingered notes agree most with the current plain decode `solveHand(seq, ctx).fingers` (ties: the lowest k). Build the target path `y+` by a constrained decode: `pinned` = every note where `golds[k*][i] !== 0`; `soft = true` so an impossible pin still yields a finite path (if `relaxed`, skip the example this epoch and count it in `skipped`). Unfingered notes thus get the model's own best fingers given the expert's.
3. **Most violating path.** `ŷ = solveHand(seq, ctx, { pinned: empty, forbidden: empty, soft: false, unaryExtra: (i, f) => (golds[k*][i] !== 0 && f !== golds[k*][i] ? -rho : 0) })` (a wrong finger on a fingered note is made cheaper by `rho`, so the decoder finds a path that is cheap **and** wrong where possible).
4. **Loss.** `hamming = count of fingered notes where ŷ differs from golds[k*]`; `loss = max(0, dot(w, Φ(y+)) − dot(w, Φ(ŷ)) + rho · hamming)`.
5. **Update** when `loss > 0`: `d = Φ(y+) − Φ(ŷ)`; `τ = min(C, loss / squaredNorm(d))` (skip when the norm is 0); `w ← w − τ · d`; if `projectPenalties`, set `w[id] = max(0, w[id])` for every `isPenaltyRule(id)`. Count an update.
6. **Averaging.** Keep `wSum` and `count` so that the averaged weights after each epoch are `wSum / count` with the standard lazy trick (`u` accumulator with timestamps) or a plain running sum updated after every example (simple and fine at this size).
7. After each epoch compute `trainAccuracy` (on the examples, averaged weights) and `validationAccuracy` (if given) with `evaluateExamples`; call `onEpoch`.
8. Return the averaged weights of the best validation epoch (or the last epoch without validation), rounded to 6 decimals, with `features: RULE_IDS`.

export interface ConfidenceSample {
  margins: number[];
  chosen: number;
  correct: boolean[];
} // margins[f] = marginal cost of finger f (1..5 → index 0..4) minus the minimum; chosen = index of the solver's finger; correct[f] = finger f matches at least one annotator
export function confidenceOf(margins: number[], f: number, temperature: number): number; // exp(-m_f/T) / Σ exp(-m_g/T) over finite margins
export function negativeLogLikelihood(samples: ConfidenceSample[], temperature: number): number; // −Σ log Σ_{f correct} p_f ; samples with no correct finger are skipped
export function fitTemperature(
  samples: ConfidenceSample[],
  opts?: { lo?: number; hi?: number; iterations?: number },
): number; // golden-section search on log T in [log 0.2, log 20], 60 iterations, minimising NLL
export function expectedCalibrationError(
  conf: number[],
  correct: boolean[],
  bins = 10,
): {
  ece: number;
  buckets: Array<{ lo: number; hi: number; count: number; confidence: number; accuracy: number }>;
};

## Corrections from the learning prototype (binding; `docs/research/learning-prototype.md` section 7)

The prototype ported the engine's features to Python (parity on 36,099 of 36,099 fingers against the TypeScript engine, `research/learn/results/engine_parity.json`) and measured every design choice on the PIG validation pieces. Where the text above disagrees with this section, this section wins.

1. **Task 0, `pathFeatures`.** Phi must reproduce exactly the terms the decoded path is charged, including the `template` bonus (M2 Task 8 landed; the Parncutt set has `template: 2`) and the free same-finger slot in slices with more than five notes. Read `solve.ts` and `templates.ts` to see where the template bonus and the slice constraints enter, decode in the trainer through the same function the identity test uses, and pass the same template matches to the loss-augmented decode. A soft (relaxed) decode charges the penalty instead of the terms on sounding-same-finger slots; Phi follows the same rule.
2. **Task 1.** `tr:<g><f>:<dir>` also fires when g = f (hops; among the largest learned weights). `shiftFast` is a different-slice term only. Generate the Parncutt regression fixture from the engine as it is now (template weight 2).
3. **Task 2.** The validation list exists: read `research/data/splits/pig_validation.json` (20 pieces: 031 034 038 039 041 046 052 053 066 076 077 080 082 083 098 117 118 119 120 138, drawn with `random.Random(20261013)` by `research/scripts/make_pig_validation.py`, tested in `research/tests/test_pig_validation.py`); do not recompute it in TypeScript. Counts confirmed: Beringer 83 pieces, textbook 672.
4. **Task 3, infeasible targets.** Never skip an example whose target violates a hard rule (28 percent of expert hand-annotations do, mostly legato overlaps with a median of 49 ms). Build `y+` by the constrained decode with `soft: true` and use its path as the target even when relaxed.
