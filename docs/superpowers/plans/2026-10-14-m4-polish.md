# M4 Polish Implementation Plan (from the first qualitative UI review)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix the usability gaps the first section 3.10 review found (`docs/reviews/ui-2026-10-14.md`, build e3cfe3a) without changing the engine: playback controls reachable while the score scrolls, a sane arrival on phones, feedback while the piano loads and counts in, a visible cursor, finger numbers explained, developer text hidden, the file drop reachable, and practice controls that say what they mean.

**Architecture:** apps/web only. The score view gets a sticky bottom dock holding Play/Pause/Rewind and the keyboard; the cursor becomes a single red mark per onset (a thin bar across the current system in addition to the red noteheads is **not** allowed, since that would be two red roots: keep the noteheads red and make the mark bigger by also colouring the stem and flag of the current notes, or switch to one bar across the system and stop colouring noteheads; the task below decides on the measurement). Every change keeps the red element rule and the color guard.

**Tech Stack:** as M4. No new dependencies.

**Depends on:** M4 (all tasks) and M6-B merged (both edit `Transport.tsx`, `SidePanel.tsx`, `ScoreView.tsx`, `DropZone.tsx`); runs after them, before M5's app tasks (M5 builds on these files).

**Spec:** product spec section 9; verification spec 3.9 and 3.10; the review's ranked list (items 1 to 4 and 7 to 10; items 5 and 6 are engine work in M3 and M5).

## Global Constraints

- M4 Global Constraints hold (one red element in every state; no color literal outside `tokens.css`; motion 120 to 200 ms; 360 px layout; LCP under 2 s; bundle budget 150 KB with Verovio lazy; parsing, solving and layout in workers).
- Every fix adds or changes a Playwright test in the existing suites (`e2e/score.spec.ts`, `playback.spec.ts`, `states.spec.ts`, `library.spec.ts`) and keeps `expectOneRed` and axe in every state; the visual baselines are regenerated once at the end (`--update-snapshots`) and committed.
- `pnpm verify` stays green after every task; implementers do not run git.

## Review Focus

1. The sticky dock must not cover the last system of the score or the side panel on a phone (padding-bottom equal to the dock height). Pinned by Task 1 (`the last system is fully visible above the dock at 360 px`).
2. Scrolling to the top on a view change must not fight the cursor's own scroll during playback. Pinned by Task 2 (`playback scroll still follows the cursor after a view change`).
3. The count-in display must never light a note before it sounds. Pinned by Task 3 (`no note is red during the count-in; the status line counts`).
4. The bigger cursor must remain exactly one red root per onset group under `expectOneRed`. Pinned by Task 4 (`states.spec: playing`).
5. The practice controls' new copy must fit at 360 px without horizontal overflow. Pinned by Task 6 (`no horizontal overflow with the practice section open`).

### Task 1: Sticky dock with Play/Pause/Rewind and the keyboard; Space toggles playback

Tests: `playback.spec.ts`: after playing to bar 10 of K.545 (silent audio), the Pause button is within the viewport (`boundingBox` inside `viewportSize`), pressing Space pauses, pressing Space again plays; `states.spec.ts` at 360 px: the last `.score-sheet svg` system's bottom edge is above the dock's top edge when scrolled to the end; `expectOneRed` in every state. Implementation: `.dock { position: sticky; bottom: 0; background: var(--paper); border-top: 1px solid var(--gray-2) }` holding the transport's primary buttons and the keyboard; `.score-layout` gets `padding-bottom` equal to the dock height (CSS variable `--dock-h`, measured with a ResizeObserver); a `keydown` handler on `document` toggles play on Space when no input, select or button is focused and no text is being typed.

### Task 2: Arrival on a phone and scroll to top on view change

Tests: open K.545 from the bottom of the library at 360 px: after the score is ready, `window.scrollY` is 0 and the title and the Play button are inside the viewport; going back restores the library scroll position (within 50 px); during playback the cursor's own scroll still works (`scrollY` increases over 3 s). Implementation: in `App.tsx` an effect on `view` calls `window.scrollTo({ top: 0 })` (not while `playback.playing`); the library stores its scroll position in the store before opening a piece and restores it on return. Below 480 px the practice controls (tempo, hands, metronome, count-in, loop) sit in a `<details>` element titled `Practice` under the dock, closed by default.

### Task 3: Feedback while loading the piano and during the count-in

Tests: with the real instrument intercepted by a Playwright route that delays sample responses by 1 s, pressing Play shows `Loading the piano…` in the status line until playback starts; with the silent instrument and count-in on, the status line shows `1`, `2`, `3`, `4` in turn before the first note and no `.is-red` exists inside `.score-sheet` during the count-in (the Play/Pause button stays the red element); the first note turns red when it sounds. Implementation: `Transport` gets `onCountInBeat(beatIndex, beats)`; `usePlayback` exposes `loading` and `countIn: { beat, beats } | null`; `useCursor` ignores positions before the first note's onset.

### Task 4: A visible cursor and visible pressed keys

Tests: on a phone (360 px), the red pixel area of the cursor is at least four times the area of a single notehead (measure with a `page.screenshot` of the sheet and count `rgb(227, 0, 15)` pixels; or assert that `.is-red` covers the note's `g.note` including `g.stem` and `g.flag` children by bounding boxes); pressed keys use `--gray-2`; in one-hand mode the muted hand's keys get `.is-muted` with 40 percent opacity; `expectOneRed` in the playing state still passes (the cursor's red roots are the current onset's `g.note`/`g.chord` elements only). Implementation: `setCurrent` keeps marking the note groups (stem and flag are their children, so `svg .is-red *` already colours them: verify Verovio's markup and, if stems live outside `g.note`, add the stem's `g` by `data-startid` lookup only when it belongs to the same note), and the CSS for `svg .is-red .notehead` raises stroke width to 2 px for the current notes; keyboard CSS changes; `data-hand` is already on keys.

### Task 5: Explain the finger numbers; hide developer text; say when the editor's fingering is shown

Tests: the library welcome shows the line `Finger numbers: 1 is the thumb and 5 the little finger, in both hands. The upper staff is the right hand, the lower staff the left.`; the score side panel shows the same line and a `Details` toggle that hides the timing line and the reader warnings by default; when the editor's fingering toggle is on, a line above the score reads `Showing the editor's fingering`; the about page keeps its text; axe clean. Implementation as the copy says.

### Task 6: Practice controls that say what they mean; file drop reachable

Tests: the tempo control shows `70 % · ♩ = 70` for Twinkle (100 qpm) at 70 percent and updates with the piece's tempo; the tempo factor resets to 100 percent when a different piece opens (store: tempo factor is per piece, kept in the per-piece slice; the M5 plan's per-piece store is not here yet, so keep a small `tempoByPiece` map in the settings slice); the hand-size select has a help line `Hand size changes the stretches the fingering allows. Choose child or small for small hands.`; a loop whose `from` is after `to` shows `The loop needs "from" before "to".` and is not applied; the library welcome has a link `Open your own MusicXML file` that scrolls to the drop zone and focuses its button; no horizontal overflow at 360 px with the practice section open.

### Task 7: Visual baselines, docs, verify

Regenerate the visual baselines (`pnpm --filter @digitus2/web exec playwright test --project=visual --update-snapshots`), check each PNG stays under 300 KB, update `docs/app.md` (new states, the dock, the re-measured K.545 open time and LCP from this build), run `pnpm verify` (all steps) green.
