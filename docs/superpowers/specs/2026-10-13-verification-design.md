# digitus2 — Verification Design

- Status: binding. Complements the product spec (`2026-10-13-digitus2-design.md`, section 8). The verification core is built together with the first solver, not after it.
- Why this document exists: the verification system is the only judge of quality between human reviews, so it has to be objective, hard to game, diagnostic enough to drive the next iteration, and faithful to what the user actually wants: fingerings that are good and easy to read for beginning-to-intermediate pianists.

## 1. Goals

## 2. Oracles

An oracle is a source of truth the engine is compared against. Several independent oracles with different failure modes are the point: an engine tuned to one of them cannot quietly overfit it.

1. PIG expert annotations (Nakamura, Saito, Yoshii 2020): 150 pieces, 309 annotations, up to 5 annotators per test piece. Official test split for gates, train split for learning, never mixed. Cross-checked scorer: the Python metrics match the official C++ evaluator to 5e-7; the TypeScript port must match the Python on real files.
2. Mutopia editorial fingerings: finger numbers typeset by editors in public-domain editions, extracted from LilyPond sources. Different people, different repertoire (method-book and intermediate pieces), different convention (editors print only what matters). The train half may fit the shippable weights; the test half is a held-out oracle, never used for tuning (section 4, item 5).
3. Textbook oracle: generated pieces whose correct fingering is canonical and exact: major and minor scales (harmonic and melodic) over one, two and three octaves in all keys, arpeggios of major, minor, dominant seventh and diminished chords, chromatic scales, in both hands and in parallel motion. The expected fingerings come from standard pedagogy tables and are stored as data with a citation each. This oracle is exact, cheap, and covers precisely what beginners practice.
4. Expert base rates: for every lint rule, the rate at which PIG annotators violate it. Rules with a zero base rate become hard gates; the others become soft rules with the measured rate as the yardstick. The data decides which rules are laws and which are preferences.
5. Baseline consensus: every third-party implementation that runs (the configurations in `research/baselines/results_table.md`) is scored on the same split. Notes where strong baselines and annotators all agree but the engine differs are surfaced first in the error gallery.

## 3. Checks

### 3.1 Unit tests

Next to the code, written before the implementation. Readers and writers round-trip; the solver has hand-constructed cases with known answers; every lint rule has positive and negative examples.

### 3.2 Benchmark command

`digitus2 bench` runs the engine over an oracle and writes a scorecard (`benchmarks/runs/<git-sha>-<label>.json`, plus `benchmarks/latest.json`): every metric from section 1 that the oracle supports, per piece and aggregated, the engine version, parameter-file hashes, and timing. It compares with `benchmarks/floor.json` and with the previous run, prints the deltas, and exits non-zero on a floor breach. `pnpm verify` calls it.

### 3.3 Error gallery

Every bench run writes `benchmarks/errors/<run>/<piece>.md`: for each mismatch, the bar, the surrounding notes with their pitches, the engine's finger with its confidence and cost breakdown, every annotator's finger, and whether the note is a hard error. Hard errors sort first. This is what the next iteration reads; a number alone does not say what to fix.

### 3.4 Metamorphic suite

Properties that hold without any ground truth, run on PIG and library pieces:

- Octave transposition: shifting a piece by an octave within the comfortable range leaves fingers unchanged.
- Mirror symmetry: reflecting pitches about an axis and swapping hands maps fingers onto themselves.
- Tempo scaling: changing tempo by a moderate factor changes fingers on at most a small, reported share of notes.
- Repeated passages: identical passages in identical context get identical fingers.
- Locality: editing bars far away does not change a passage's fingering.
- Pin idempotence: pinning the engine's own output and re-solving changes nothing; pinning one note changes only a bounded neighborhood.
- Determinism: two runs produce byte-identical output.

### 3.5 Lint

`digitus2 lint` reports every rule violation with its severity (law or preference) and the expert base rate. The gate for laws is zero. Soft rules are reported against the base rate. Lint runs on engine output, on user edits in the app (as advice), and on the oracles themselves (which is how base rates and annotation errors are found).

### 3.6 Readability

A printed fingering is a subset of the complete fingering. The minimal-sufficient reduction prints a digit only where the validated player model fails to reconstruct the engine's finger in a greedy forward pass, plus the first note of each hand, pinned notes and notes below the confidence floor; one digit per chord. The player model is a deterministic rule set (rules R0 to R5 in `docs/research/readability.md`, section 7.1): a printed digit sets the anchor; a repeated pitch keeps the finger; a step of one or two semitones moves to the adjacent finger; otherwise the finger implied by the anchor with semitone/2 steps; chords fill from the nearest printed chord note; and a repeat memory for recurring segments, which requires the engine to finger repeats identically. Inferability is 100 percent by construction. Density is reported per level against the floors and targets in the goals table and against the editors' density on Mutopia pieces; the reduced density must not exceed the editor's on the same piece.

A list of context triggers (print after a position change, at a crossing, on the first note of a passage, on wide leaps, on chord outer voices, where the engine's confidence is low, and wherever the complete fingering would otherwise be ambiguous) is not used: measured on 286 editorial parts it scores below chance as a predictor of what editors print and would print 60 percent of notes.

The app prints the reduced set by default with a toggle to show all. This is part of M5 and is not built: the app prints every digit.

### 3.7 Ease profiles

For the beginner and intermediate profiles the scorecard reports position changes, maximum spans, thumb and fifth finger on black keys, and finger substitutions, each against the expert median for the same pieces, and per library level.

### 3.8 Calibration and ablation

Confidence buckets against actual error rates give the expected calibration error. Correctness is counted per annotator: a note's target is the share of its annotators who use each finger, the temperature is fitted by the cross-entropy against that share, and a bucket's accuracy is the mean share of annotators who use the chosen finger, so the error does not depend on how many annotators a piece has (PIG validation has 1.2 per piece, the test split 5). `digitus2 bench --ablate` zeroes each rule weight in turn and reports the metric deltas: a rule whose removal changes nothing is flagged for review; a rule whose removal improves the target is a bug or a wrong weight.

### 3.9 Application checks

Playwright end-to-end flows for: open a library piece, see printed fingerings, play with the cursor moving, toggle editor's fingering, export (and edit a finger and watch the re-solve, once M5 exists). In every captured state a DOM check asserts exactly one element carries the red token (the design brief as a test). Axe runs on each page; screenshots are compared against stored baselines for the score view and the library.

### 3.10 Qualitative UI review (periodic, by a subagent)

While the app changes, an independent Opus subagent (intended daily) opens the deployed or locally served app in a browser, uses it as a beginner would (open a library piece, read the fingering, play, edit a finger once possible, import a file, export), and writes `docs/reviews/ui-YYYY-MM-DD.md`: is it clear what to do next, do the main features work, is anything cluttered or confusing, does the black-and-white-plus-one-red brief hold on every screen, what would a piano teacher object to. Each review ends with a ranked list of concrete fixes; the top items become tasks. The reviewer never edits product code. The user asked for this review.

### 3.11 Cross-implementation agreement

The TypeScript metrics and the Python metrics are run on the same prediction files inside `pnpm verify`; a disagreement above 1e-6 fails.

### 3.12 Teacher review (weekly, qualitative)

Piloted in `docs/research/teacher-review.md`: a blinded Opus reviewer reads a two-to-eight-bar passage rendered as text with a candidate fingering and returns a structured judgement against a rubric (physically possible, idiomatic, economical, consistent, beginner-friendly) with objections located by bar and note. On 40 PIG test passages in three conditions (expert, FHMM3, expert with planted faults; 240 blinded reviews) it found 99 percent of planted faults within one note, raised 2.5 objections per 100 notes on expert fingerings (0.64 per passage), ranked expert above corrupted in every case, flagged disputed notes three times more often than unanimous ones, and agreed with itself across two runs (Pearson 0.95 on scores). It is used as a weekly job next to `pnpm verify`, never inside it: the 20 lowest-confidence passages, every hard-error gallery entry, 10 random level 1 to 3 library passages as control, and user-edited passages (once M5 stores edits) are rendered, dispatched in blinded batches of eight, and objections that two reviewers share (or any error-severity objection) become hypotheses in `docs/experiments.md` for the quantitative loop. No floor depends on it, it is never a number to tune on, and it never runs on PIG data in any shipped artefact. The legend states that `dur` is sounding length (early release and pedal are normal), and a recall control (composer hidden or passage transposed) checks that the reviewer reads rather than recalls. The reviewer brief and wrapper are in `research/teacher_review/README.md`; the job is `research/teacher_review/weekly.py`, and each run writes `docs/reviews/teacher-<date>.md`. The hard-error set comes from a bench on the PIG validation pieces, never the test split, capped at 4 windows per piece.

## 4. The iteration protocol (how autonomy stays honest)

1. State a hypothesis in `docs/experiments.md` (lab notebook): what changes, which metric should move, by how much.
2. Change code or parameters on the working tree.
3. Run `pnpm verify`. The bench prints deltas; the error gallery explains them.
4. Accept when the primary metric (gen on the PIG test split, or the oracle the experiment targets) improves without any floor breach and without a readability or lint regression; raise floors in the same commit. Reject otherwise and revert; record the outcome either way.
5. Never tune on the test split: parameter learning uses the PIG train split and the textbook oracle only, with one exception. The Mutopia corpus is split by piece (`research/data/splits/mutopia_split.json`, seed 20261013, 70/30). The train half may be used to fit the shippable weight set because PIG-fitted weights cannot be distributed; the test half remains a held-out oracle and is never used for tuning.
6. Every milestone ends with a scorecard row appended to `benchmarks/history.md` and the goals table in this document updated with actual numbers.

## 5. Milestone placement

- M1 (foundation): metrics, PIG and MusicXML IO, CLI, `pnpm verify` skeleton.
- M2 (solver v1 with verification core): `digitus2 bench` with scorecards and error galleries, lint with base rates, textbook oracle, metamorphic suite, floors raised to the solver's first real numbers.
- M3 (learning): train-split parameter fitting, calibration, ablation, Mutopia oracle wired in, baseline consensus in the gallery.
- M4 (app): one-red-element check, axe, Playwright flows, visual baselines.
- M5 (interaction): the readability reduction and its gate (section 3.6), not built.
- M7 (verification complete): everything in section 3 running under `pnpm verify` and CI (3.10 and 3.12 as scheduled jobs beside it), goals table filled with measured values. Still open: the readability and ease rows of the goals table.
